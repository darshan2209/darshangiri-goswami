01 / Detection & response

Detection Engineering Lab

Zeek watches the wire and writes structured connection, DNS and HTTP logs. Apache Kafka carries them into a Wazuh/OpenSearch indexer, so a slow consumer queues instead of dropping events. On top sit 12 detection rules I wrote and tuned, and MISP indicators pulled in over its REST API so new intelligence enriches alerts without anyone retyping it.

  • Zeek
  • Apache Kafka
  • Wazuh
  • OpenSearch
  • MISP
  • Ubuntu
Read the write-up

The rules cover SSH brute force, brute force followed by success, long and bursty DNS queries typical of tunnelling, MISP domain and IP hits, system and auth-config file modification, new account creation, privileged execution from auditd, Zeek notices, and scripted HTTP clients. I tuned them against replayed attack traffic, which is where the noisy ones showed themselves.

Windows and Linux endpoints are onboarded for central collection, and file integrity monitoring surfaced 100+ unauthorised file changes triaged from one dashboard. Decoupling collection from indexing through Kafka is the part I would defend hardest: it is what stops a backed-up indexer from becoming lost evidence.

02 / Identity & governance

Authorization Concept Toolkit

Turns a raw entitlement export into an audit-ready authorization concept (Berechtigungskonzept), then runs the four checks that keep it true: segregation of duties, candidate business-role mining, per-owner access certification campaigns, and access-hygiene findings. Automated system accounts are treated as first-class identities, because they hold entitlements and breach the same rules but have no manager to review them.

  • Python
  • IGA
  • Segregation of Duties
  • Role mining
  • Access certification
  • ISO 27001
  • DORA
Read the write-up

A written authorization concept is a regulatory expectation in financial services, and it is usually a document that was accurate on the day it was signed. This generates the document from the same export the checks run on, so the concept and the estate cannot drift apart, and regenerating it is one command rather than an annual project.

On the sample estate it finds 7 segregation-of-duties conflicts, three candidate business roles explaining 78% of all grants, and 13 access-hygiene findings. Two of the seven conflicts sit on service accounts: svc-payment-gateway can both create and release a payment, which is the four-eyes control failing in the population nobody recertifies. Every control is mapped to ISO/IEC 27001:2022, NIST SP 800-53 R5 and DORA, and 27 tests pin the behaviour that is easy to get subtly wrong, such as a conflict being per identity rather than per team.

03 / Identity & governance

Governed Multi-Agent Consultation

A reference implementation of what a team of LLM agents needs before it can be trusted in a regulated operation: consultation only under an explicit grant that can only narrow, with an RFC 8693-style actor chain showing on whose authority each step ran; disagreement typed and escalated instead of averaged away; an answer that says what it no longer covers when a specialist is down; and an append-only record a person can contest and overrule.

  • Python
  • Multi-agent AI
  • RFC 8693
  • Delegation
  • Explainable AI
  • Audit trail
Read the write-up

The worked scenario is a distribution grid operator deciding whether to approve 250 kW of new solar on one feeder without a reinforcement study, with five agents each holding part of the answer. Every fact carries a vintage, which lets the coordinator tell a split caused by stale data, reconcilable without a person, from a genuine difference of judgement, which always goes to one.

The reference agents are deterministic on purpose: the properties under test belong to the coordination layer, and a sampling temperature deciding whether a test passes would make the evaluation worthless. The same interface takes a model-backed agent. 26 tests run in milliseconds with no network and no API key, and the README says plainly what the design does not yet do.

04 / Systems & cloud

Linux Hardening Lab

An Ubuntu Server baseline hardened against the CIS Benchmark: key-only SSH, PAM password policy, kernel sysctl parameters, services stripped back and host firewall rules. The whole checklist became a Bash script that applies it and then re-verifies itself on a fresh host, measured by Lynis before and after.

  • Ubuntu Server
  • Bash
  • auditd
  • Lynis
  • CIS Benchmark
Read the write-up

The script is idempotent: run it twice and the second run reports nothing to change. It also refuses to disable password authentication until it can see a working authorized_keys, because a hardening script that locks you out of your own box is not a hardening script.

auditd rules record privileged command execution and access to sensitive files, and those events forward into the detection pipeline above. That link is the point of the lab: a host change is not really monitored until it is alertable somewhere else.

05 / Systems & cloud

Multi-Cloud Posture Lab

I built an AWS account wrong on purpose, with over-permissive IAM, a public S3 bucket and logging switched off, then remediated each finding back to least privilege and traced every CloudTrail and GuardDuty detection to the exact setting that produced it. Repeated on Google Cloud and Oracle Cloud, plus an admin review of Google Workspace and Microsoft 365.

  • AWS IAM
  • CloudTrail
  • GuardDuty
  • S3
  • GCP
  • Oracle Cloud
  • boto3
Read the write-up

A boto3 script does the repeatable part: flagging wildcard permissions and unused credentials across the account, run before and after remediation so the diff is the evidence. On GCP and Oracle the same review shape held. Turn on audit logging, read the IAM bindings, and both surfaced service accounts holding far more than they used.

An honesty note I keep with this lab: GuardDuty on a fresh empty account produces nothing by itself, so the findings here are its sample findings, each mapped to the misconfiguration class it represents. Useful for learning the finding-to-cause path, not a claim of live attacker traffic.

06 / Systems & cloud

Kubernetes Security Lab

A k3s cluster with RBAC scoped to least privilege, namespace network policies restricting east-west traffic, and pod security standards enforced at admission. Then I deployed a deliberately vulnerable workload and reconstructed what happened from the cluster audit log.

  • k3s
  • RBAC
  • NetworkPolicy
  • Pod Security
  • Calico
Read the write-up

Two things this lab taught me that reading would not have. First, k3s ships with Flannel, which accepts NetworkPolicy objects and silently ignores them; the policies only actually enforce after swapping in Calico. A control you believe in but that does nothing is worse than no control.

Second, the honest version of "which controls caught it": pod security admission rejected the privileged pod before it was ever scheduled, so the network and runtime controls were never tested by it. The compliant workload and the labelled/unlabelled probes are what demonstrate those.

07 / Systems & cloud

Network Segmentation & Secure Tooling

The segmented network the detection lab runs on: management, endpoint and DMZ VLANs, the Zeek sensor on a mirror port, firewall zone rules between them. Alongside it, the secure-development practice applied to everything above: input validation, credentials held in the environment, static analysis and dependency scanning.

  • VLANs
  • DMZ
  • SPAN port
  • nftables
  • Bandit
  • pip-audit
Read the write-up

Segmentation came first, not last. Putting the sensor on a mirror port off the right segment is what makes the Zeek logs worth anything; a sensor on the wrong side of the firewall produces tidy logs about nothing.

On the tooling side, every script that touches an API reads its credentials from the environment, validates what comes back, and goes through Bandit and pip-audit. Detection tooling runs with privileges, so it is exactly the code that should not be the soft spot.

AI-Assisted Monitoring & Automation

An AI-assisted workflow that monitors an event stream, flags exceptions with a Python anomaly-detection step, then sends them to an AI platform over REST for triage, risk scoring and playbook mapping. It produces response recommendations for a human to approve, never to execute on its own.

  • Python
  • AI Platform API
  • REST API
  • Risk scoring
  • Human-in-the-loop
Read the write-up

Pipeline: ingest a simulated event stream, then a Python anomaly-detection step scores each event, then exceptions go to an AI platform via REST API for triage, risk scoring and playbook mapping, and structured recommendations are logged for human review. The guardrails are deliberate: a human decides, and every score comes with the reasoning that produced it.

09 +2.2 kBPer handshake for hybrid X25519MLKEM768

09 / Cryptography

Post-Quantum TLS Benchmark

A reproducible benchmark of ML-KEM (FIPS 203) against RSA-2048 and X25519: key and ciphertext sizes, median timings over 30 runs, and the wire overhead of the hybrid X25519MLKEM768 group that TLS 1.3 deployments use. The finding is that for this migration, message size rather than computation is the binding cost, at about 2.2 kB extra per handshake.

  • ML-KEM
  • FIPS 203
  • TLS 1.3
  • X25519
  • Python
  • Post-quantum
Read the write-up

The hybrid group's key shares are 1,216 bytes from the client and 1,120 from the server, against 32 bytes each for plain X25519. Those sizes are fixed by the specifications, so they hold for any implementation, and they are what the protocol-level analysis rests on.

An honesty note on the timings: ML-KEM ran on a pure-Python reference implementation while RSA and X25519 went through OpenSSL's optimised C, so the ML-KEM times are pessimistic upper bounds, not a speed comparison. The benchmark comes with a research paper I wrote for my MSc Cryptology module.

      the agents?
      
      
      My M.Sc. research asks a narrow question: eight widely used security and AI-governance instruments all govern identity, so what happens when a machine identity's authority passes to an AI agent? The short answer is that none of them states a requirement an auditor can test.
